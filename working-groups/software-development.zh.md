# 软件开发组

[English](software-development.md) · [全部工作组记录](README.md) · [研究方法](method.zh.md)

`polished_software_dev` 是 The One 开发软件的默认团队：一个以最高推理强度运行、可以启动助手的方案领队。
它就是[《固定模型之上的智能体团队》](../papers/2026-11-teams-on-a-fixed-model)中在 Terminal-Bench 4.1 上测量的那个配置。
这篇记录说明它为什么在 2026 年 11 月 27 日有了自己的题单，题单是怎样建起来的，以及它的第一个基线。

## 为什么要有自己的题单

这个团队和前端设计组共用前端技能，所以这个技能每改一次，团队的版本就跟着变一次。
每个版本跑一次 Terminal-Bench 4.1（最高强度下 189 次尝试），代价太高，没法这样频繁地重复；
而且由终端谜题组成的基准，很难说明这个团队每天做的工作：修改一个大型产品。

## 题单

- **候选池共三十项任务**，都是公司已经在 The One 自己的代码里完成过的，分五层，每层六项：
  智能体内核与运行时；本地服务的功能与 API；桌面渲染进程的行为；插件、SDK 与注册表；应用之外的工具与服务。
  其中二十一项是功能或行为变更，九项是缺陷。
- **选出十五项**，每层三项，规模从小到大；**留出五项**，按固定种子随机抽取，每层一项。
  留出题的题目包由智能体构建，这些智能体只回报每个题目包是否建成，
  以及其验证输出的最后一行（能抓出多少个缺陷，有多少个正确的变体通过）；我们从不打开这些题目包。
- 每道题都从被采纳的那次改动之前的提交开始，按原样给出当时的请求，
  并从产品外部检查结果：项目自己的测试套件、经 HTTP 访问的运行中服务、浏览器里的渲染进程，
  再加上产品的章程规则（例如，智能体遇到错误会永远重试；改动不得给重试设上限）。
- **打包时在题目镜像里发现了三处故障**，那时还没有跑任何试验，每一处都在所有题目包里修好了：
  仓库解包后是组可写的，应用会正确地拒绝这样的插件文件夹，于是有一项功能返回了与题目无关的错误；
  缺少一个 GUI 库，测试套件在收集阶段就被中断，什么都没有运行；有两个镜像缺少一个可选的数据库依赖。
  修好之后，每个镜像都能离线收集项目的整套测试（视起始提交而定，为 7,788 到 13,430 个测试）。

## 基线

第一条记录来自版本 7.5，每道可读题两次试验，每道留出题也是两次：

| | 结果 |
| --- | --- |
| 可读题 | 20 次试验通过 15 次，平均 0.750 |
| 留出题 | 10 次通过 8 次 |

逐一读过可读题上的失败：一条针对某个成员提出的规则，只用在了这个成员身上，
没有用到同类的其余成员（2 次中 0 次通过）；一个改动涉及已上线工作组的文件，
却没有提高该工作组的版本（2 次中 0 次通过）；另有一道题两次中通过一次。
在这条记录之前，读过最初几次尝试后修正了四项检查（一项检查的措辞、一个键盘关口、一个时间上限、尽力而为的截图）。

随后，版本 7.5 在 main 上被撤回（它带的浏览器页面检查被回退了；见前端设计组的记录），
所以这份题单要等团队的下一个版本。

## 搭建题单的收获

- 智能体打包的题目，要等我们自己重跑过它的验证才算数；
  第一次这样做时，我们自己的“重跑”根本没有运行（一条转入后台的命令收到的是空脚本），我们是在列出输出时才发现的。
- 环境故障值得在第一次试验之前就去排查。部署运维组的镜像里也缺这个 GUI 库：
  那些试验的 434 份记录中有 197 份出现了它。那里每个版本遇到的都是同样的镜像，所以那些比较仍然成立，
  但团队因此损失了一些轮次。
